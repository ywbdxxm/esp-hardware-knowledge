# ESP 硬件文档知识层设计

日期：2026-08-16
状态：架构方向已确认，书面规格待用户复核

## 1. 背景

本机目前保存 ESP32-C3 与 ESP32-S3 的中文数据手册、技术参考手册、模组手册和硬件设计指南，共 14 份 PDF，约 43.09 MiB。部分技术参考手册超过一千页，包含中文正文、寄存器表格、时序、电气参数和框图。

普通 PDF 文本提取会破坏其中的中文内容。Docling 配合 RapidOCR 的整页识别能够较好恢复正文、表格和图片，但任何自动转换都可能产生 OCR 错字、表格错位或页码映射误差。因此，结构化资料只用于检索和定位，原始 PDF 始终是最终权威来源。

## 2. 目标与非目标

### 2.1 目标

- 将现有 ESP32-C3、ESP32-S3 PDF 转换成可搜索、可审阅的 Markdown、图片和结构化元数据。
- 让 Codex、Claude Code、OpenCode、Hermes 以及普通终端通过同一套本地接口检索资料。
- 每条结果都能回溯到芯片、文档、文档版本、原始 PDF 路径和 PDF 页码。
- 在自动提取不可靠时，直接定位并渲染原 PDF 页面供调用方核对。
- 使用成熟组件完成解析和检索，不自行实现通用 RAG 框架。
- 代码、设计、配置、测试和后续 Skill 可以进入 Git；生成资料、数据库、模型、缓存和日志只保存在本机。

### 2.2 非目标

- 第一阶段不部署 RAGFlow、Dify 或常驻 Web 服务。
- 第一阶段不使用向量数据库、嵌入模型、LLM 摘要或自动生成“标准答案”。
- 不把生成的 Markdown 当作原始 PDF 的替代品。
- 不承诺自动解析结果本身绝对正确；系统保证的是证据可追溯、低可信内容不会被伪装成确定事实。
- 不为单一 AI 客户端建立专用数据库或复制语料。

## 3. 总体架构

```text
原始 PDF（只读、权威来源）
        |
        v
Docling + RapidOCR（结构化解析）
        |
        +--> 分页 Markdown / 图片 / 表格
        +--> 文档清单 / 版本 / SHA-256 / 页码映射
        |
        v
SQLite FTS5（本地关键词、短语、字段过滤）
        |
        v
espdocs CLI（稳定的文本和 JSON 接口）
        |
        +--> Codex Skill
        +--> Claude Code / OpenCode / Hermes 适配说明
        +--> 人工终端查询
        |
        v
低可信、冲突或关键参数 --> 原 PDF 指定页面 / 页面渲染图
```

边界如下：

- Docling 负责文档理解和结构化，不负责回答问题。
- SQLite FTS5 负责确定性检索，不负责生成结论。
- `espdocs` 负责导入、查询、证据输出和原文回退，是本项目唯一稳定接口。
- Skill 只描述调用工作流和安全规则，不包含语料，也不成为唯一入口。
- MCP 可以后续作为 `espdocs` 的薄适配层加入，但不能成为使用资料库的前提。

## 5. 数据模型与来源追踪

每份文档至少记录：

- 稳定文档 ID；
- 芯片或模组型号；
- 文档类型；
- 标题、语言、版本和发布日期（能够从文档确认时）；
- 原始绝对路径、文件大小、修改时间和 SHA-256；
- PDF 总页数、导入时间和解析器版本；
- 导入状态、警告和失败原因。

每个可检索内容块至少记录：

- 文档 ID 和块 ID；
- PDF 页码；
- 印刷页码或章节页码（能够可靠识别时单独保存）；
- 章节路径和内容类型；
- 正文、表格 Markdown 或图片说明；
- 原图、页面渲染图或表格文件的相对位置；
- 解析方式与验证状态。

PDF 页码统一指 PDF 文件中从 1 开始的物理页序号。印刷页码不与 PDF 页码混用。

## 6. 导入流程

1. 扫描允许的源目录，只接受配置中声明的 PDF。
2. 计算 SHA-256，并以哈希判断新增、修改或无需处理。
3. 读取 PDF 元数据和页数，识别芯片、模组、文档类型及版本。
4. 使用固定版本的 Docling 和 RapidOCR 进行结构化解析。
5. 按 PDF 页面保留正文、表格、图片和章节关系；不得只输出无法回溯页码的整本文本。
6. 对页码覆盖、空页比例、乱码、表格数量、图片引用和异常字符执行自动检查。
7. 只有通过最低检查的文档才进入活动索引；失败结果保留日志但不替换上一版可用索引。
8. 在临时数据库中建立索引并完成自检后，再原子替换活动数据库。

导入中断、磁盘空间不足、OCR 失败或单份文件损坏时，不破坏已有可用资料库。重复导入相同 SHA-256 的文件必须得到相同的稳定文档 ID。

## 7. 检索与统一接口

第一阶段采用 SQLite FTS5，支持：

- 中文关键词、精确短语、寄存器名和信号名；
- 按芯片、模组、文档类型、文档版本和章节过滤；
- 对寄存器名、外设缩写和常用中英文术语进行可审阅的别名扩展；
- 返回匹配片段及其相邻内容，而不是生成答案；
- 无数据库时提供 `rg` 文件检索作为诊断回退。

稳定 CLI 至少包含：

```text
espdocs ingest              导入或增量更新资料
espdocs search              查询并返回候选证据
espdocs show                查看候选块及上下文
espdocs source              返回原 PDF、页码并按需渲染该页
espdocs doctor              检查依赖、源目录和索引状态
espdocs verify              执行语料完整性与检索评测
```

所有查询命令同时提供人类可读输出和版本化 JSON 输出。JSON 接口用于不同 Agent 集成，至少包含：

- 查询条件；
- 匹配分数和匹配原因；
- 芯片、文档标题、版本和章节；
- PDF 绝对路径与 PDF 页码；
- 内容片段、内容类型和验证状态；
- 页面渲染图位置（已生成时）；
- `requires_source_check` 标志及原因。

## 8. 准确性与原文回退策略

### 8.1 证据等级

- **A 级：** 原始 PDF 指定页面；调用方可以直接读取该页，或查看由哈希一致的原 PDF 按固定参数忠实渲染的高分辨率页面图。
- **B 级：** 已确认页码映射、通过自动检查，且必要时经过人工抽检的结构化内容。
- **C 级：** 未验证的 OCR、Markdown、搜索片段或别名扩展结果，只能用于定位。

检索排名高不等于证据等级高。系统不得把相似度或关键词得分解释成事实置信度。

### 8.2 强制回看原文的情况

出现以下任一情况时，`requires_source_check` 必须为真：

- 查询涉及寄存器地址、复位值、位域或保留位；
- 查询涉及绝对最大额定值、电压、电流、时序、温度或射频参数；
- 查询涉及引脚复用、启动配置、eFuse、安全或烧录风险；
- 结果来自表格、复杂框图、脚注、跨页内容或 OCR 质量警告页；
- 同一问题在不同文档、芯片、模组或版本中出现冲突；
- 页码映射失败、来源版本未知、候选结果不足或答案依赖推断。

调用方工作流必须遵守：先检索定位，再读取上下文；需要原文核对时调用 `espdocs source`，最后在回答中引用文档、版本和 PDF 页码。无法获得足够证据时，应明确说明不确定性，不得补全或猜测参数。

### 8.3 原 PDF 访问

`espdocs source` 不依赖默认 PDF 阅读器是否支持跳页。它应能：

- 输出原始 PDF 绝对路径和 PDF 页码；
- 将指定原 PDF 页面渲染为高分辨率 PNG，供视觉检查；
- 输出相邻页建议，处理跨页表格和章节上下文；
- 校验当前 PDF 的 SHA-256 与索引记录一致。

原始 PDF 哈希与索引不一致时，该索引结果立即标记为过期，不作为 B 级证据。

## 9. Agent 使用方式

所有 Agent 优先调用本地 `espdocs` CLI，因此不依赖某个客户端是否支持 MCP。

后续 Skill 只包含：

- 哪些问题需要查询资料；
- 如何添加芯片和文档类型过滤；
- 如何读取 JSON 结果与扩大上下文；
- 哪些高风险信息必须查看原 PDF；
- 回答中统一的来源引用格式；
- 无结果、冲突和工具不可用时的处理方式。

Skill 不包含硬编码答案，不复制语料，不绕过 `requires_source_check`。各 Agent 的适配文件只包装同一套 CLI 契约。

## 10. 测试与验收

### 10.1 自动测试

- 单元测试：文档识别、哈希、页码规范、别名、过滤器和 JSON 模式。
- 集成测试：增量导入、失败回滚、数据库原子替换、原文定位和页面渲染。
- 语料检查：页数覆盖、空内容比例、乱码率、无效图片引用和孤立内容块。
- 契约测试：人类输出与 JSON 输出、退出码及跨 Agent 调用保持稳定。

### 10.2 检索评测

建立可进入 Git 的人工评测集，覆盖：

- C3 与 S3 同名外设的区分；
- 寄存器、位域和复位值；
- 电气参数、引脚与启动配置；
- 表格、图片和跨页内容；
- 中文自然语言、英文术语及缩写；
- 应返回无结果或要求核对原文的问题。

每道评测题记录期望文档和 PDF 页码范围，不保存自动生成答案。第一阶段验收要求：

- 所有活动文档均有哈希、页数和版本状态；
- 检索结果全部带有原 PDF 路径和物理页码；
- 高风险类别全部触发原文核对；
- 原文页面能够独立渲染且哈希校验通过；
- 评测集中“正确来源进入前五个结果”的比例达到 95%；
- C3/S3 或不同模组的结果不得在未标注的情况下混合；
- 解析或索引失败不会损坏上一版可用资料库。

## 11. 后续升级条件

只有当真实评测表明 FTS5 无法达到召回指标时，才进入第二阶段。第二阶段可以使用 LangChain 等成熟组件接入嵌入模型、向量存储、混合检索或重排，但继续沿用现有数据模型、来源引用、CLI 和原文回退规则。

以下情况才考虑 RAGFlow：文档规模增长到人工管理困难、需要可视化切片审查、多人维护数据集，或需要长期运行的知识库服务。只有在需要构建面向最终用户的聊天应用或工作流时才考虑 Dify。

任何语义检索升级都必须用同一评测集证明收益，并不得降低来源可追溯性或绕过原 PDF 核对。

## 12. 实施顺序

1. 建立仓库结构、配置模式和运行数据隔离规则。
2. 实现文档清单、哈希、版本识别和增量导入。
3. 实现分页结构化输出及完整性检查。
4. 实现 FTS5 索引与 `espdocs` 查询接口。
5. 实现原 PDF 页面定位、渲染和哈希校验。
6. 建立检索评测集并达到验收门槛。
7. 最后编写通用工作流 Skill 和各 Agent 的薄适配说明。
